# Working in Authored UI

The purpose of this directory is beautiful, enjoyable interfaces. Do not replace the work with an evaluation framework, a numerical taste model, or a growing catalog of prohibitions.

Read the actual product brief first, then METHOD.md. DESIGN.md describes the examples, not a universal style. Start with the subject and the useful experience. Make the composition, type, imagery, and interaction specific to it.

Build and inspect real interfaces. Keep content, asset provenance, and state transitions honest. Do not fabricate reviews, customers, metrics, unavailable actions, or commercial functionality to make a screenshot look complete.

Preserve native control semantics, visible keyboard focus, reduced motion, accessible feedback, responsive reachability, and reversible local actions. Treat these as part of the implementation, not proof of aesthetic excellence.

Write consequential observations and design decisions to files. If roles are delegated, give each role a specific question and ask for a durable findings file. Do not manufacture multi-agent work when only one agent is running.

Use `escli docs` for software documentation where available. If it is absent, state that in the engineering record and consult current primary documentation. Do not silently claim that the preferred documentation tool ran.

Run the browser checks before delivery. State their actual mode and limits. Do not present in-memory browser tests as proof of real navigation, durable storage, physical-device audio, or cross-browser compatibility. Do not infer beauty from a passing smoke test.

Extend the accepted direction without copying a whole unrelated page. Keep the implementation and decisions in the requested PR. Do not merge or publish unless authorized.
